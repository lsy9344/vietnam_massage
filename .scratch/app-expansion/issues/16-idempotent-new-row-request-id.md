# 16: 새 행 요청 id로 중복 생성 막기

**What to build:** 콜에 요청 id 칸을 더한다. 비어 있을 수 있고 값이 있으면 유일하며, 기존 콜은 비워 둔다. 원장의 새 행 초안마다 화면이 요청 id를 하나 만든다. 서비스는 그 요청 id로 만든 콜이 이미 있으면 새로 만들지 않고 "이미 저장된 콜입니다"와 함께 그 콜을 돌려준다. 새 행 저장 응답이 끊기면(네트워크 오류, 시간 초과) 행은 "저장 여부 확인 중"이 되고 입력이 남으며, "다시 시도"는 같은 요청 id로 보낸다. (스펙 B07, 스토리 46–49, V06)

**Blocked by:** 15 (같은 행 저장 순서를 쓴다)

**Status:** ready-for-agent

- [ ] 같은 요청 id의 생성이 동시에 두 번 들어와도 콜 하나와 최초 생성 감사 기록 하나만 남는다. 유일성 위반으로 실패한 요청은 이미 만든 콜을 읽어 같은 응답을 돌려준다.
- [ ] 메모리 Prisma가 요청 id의 유일성 위반을 실제 DB처럼 내고, 콜 서비스 테스트가 이를 확인한다.
- [ ] 응답이 끊긴 뒤 다시 보내면 결과는 새로 만든 콜이거나 이미 있는 콜이며, 콜이 두 줄로 생기지 않는다.
- [ ] 중복 반환 때 감사 로그에 새 항목이 쓰이지 않는다.
- [ ] 마이그레이션은 기존 콜의 요청 id를 비워 두고 다른 값은 바꾸지 않는다.
- [ ] 저장 상태에 "저장 여부 확인 중"이 더해지고 두 언어 문구가 있다.
- [ ] 응답 유실을 흉내 낸 E2E로 재시도 뒤에도 콜이 하나임을 확인한다.
