# 16: 새 행 요청 id로 중복 생성 막기

**What to build:** 콜에 요청 id 칸을 더한다. 비어 있을 수 있고 값이 있으면 유일하며, 기존 콜은 비워 둔다. 원장의 새 행 초안마다 화면이 요청 id를 하나 만든다. 서비스는 그 요청 id로 만든 콜이 이미 있으면 새로 만들지 않고 "이미 저장된 콜입니다"와 함께 그 콜을 돌려준다. 새 행 저장 응답이 끊기면(네트워크 오류, 시간 초과) 행은 "저장 여부 확인 중"이 되고 입력이 남으며, "다시 시도"는 같은 요청 id로 보낸다. (스펙 B07, 스토리 46–49, V06)

**Blocked by:** 15 (같은 행 저장 순서를 쓴다)

**Status:** done

- [x] 같은 요청 id의 생성이 동시에 두 번 들어와도 콜 하나와 최초 생성 감사 기록 하나만 남는다. 유일성 위반으로 실패한 요청은 이미 만든 콜을 읽어 같은 응답을 돌려준다.
- [x] 메모리 Prisma가 요청 id의 유일성 위반을 실제 DB처럼 내고, 콜 서비스 테스트가 이를 확인한다.
- [x] 응답이 끊긴 뒤 다시 보내면 결과는 새로 만든 콜이거나 이미 있는 콜이며, 콜이 두 줄로 생기지 않는다.
- [x] 중복 반환 때 감사 로그에 새 항목이 쓰이지 않는다.
- [x] 마이그레이션은 기존 콜의 요청 id를 비워 두고 다른 값은 바꾸지 않는다.
- [x] 저장 상태에 "저장 여부 확인 중"이 더해지고 두 언어 문구가 있다.
- [x] 응답 유실을 흉내 낸 E2E로 재시도 뒤에도 콜이 하나임을 확인한다.

## Comments

- 2026-10-15 구현(브랜치 `feat/ticket-15-stale-save-rejection` 위, 티켓 15의 저장 순서와 저장 상태를 그대로 쓴다). main 병합·push는 하지 않았다.
- 데이터: `ServiceCall.requestId`(`request_id`, 비어 있을 수 있고 값이 있으면 유일). 마이그레이션은 칸과 유일 인덱스만 더한다. 이전 마이그레이션까지 적용한 Postgres에 콜 2건을 넣고 새 마이그레이션을 적용해, 다른 칸 값이 그대로(행 md5 동일)이고 요청 id가 모두 비어 있으며 같은 요청 id는 두 번 들어가지 않는 것을 확인했다.
- 서비스: 새 행은 `createServiceCallRow()`(요청 id 필수, `{ row, alreadySaved }`)로 만든다. 같은 요청 id의 콜이 있으면 아무것도 쓰지 않고 그 콜을 돌려준다. 동시에 들어와 유일성 위반(P2002)으로 실패한 쪽은 트랜잭션 밖에서 먼저 만든 콜을 읽어 같은 응답을 준다. 실제 Postgres에서 같은 요청 id 6개를 동시에 3번 보내 매번 4개가 P2002 경로로 같은 콜을 받고 콜은 하나인 것을 확인했다. 메모리 Prisma는 요청 id 중복 생성에 P2002를 낸다. `saveBasicServiceCallRow()`는 요청 id 없이 그대로 만든다(테스트와 이전 비교가 쓴다).
- 화면: 새 행은 폼 액션(`useActionState`) 대신 제어형 초안과 저장 순서(`call-new-row-save.ts`)를 쓴다. 폼 액션은 결과가 오면 텍스트 입력을 비웠고, 네트워크 오류는 오류 화면으로 보냈다. 서버 액션은 `createServiceCallRowAction`으로 바뀌었고 `saveBasicServiceCallRowAction`은 지웠다(검증 스크립트 2-1을 맞추고, 읽기 전용 화면 3-2·3-3·3-4의 금지 목록에 새 경로를 더했다).
- 결정과 가정:
  - "최초 생성 감사 기록"은 지금 생성 때 쓰는 감사 그대로다. 고객을 붙여 만든 콜만 생성 때 감사(`service_call.row_changed`, 이전 값 없음)를 남기고, 고객 없이 만든 콜은 지금처럼 감사가 없다. 스펙 29줄("감사는 바뀌지 않는다")에 따라 생성 감사를 새로 만들지 않았다. 테스트는 고객을 붙인 생성으로 "하나만"을 확인한다.
  - 같은 요청 id 조회는 쓰기 검사(운영월 잠금, 활성 기준정보)보다 먼저다. 이미 만든 콜을 돌려주는 것은 쓰기가 아니라서, 그 사이 운영월이 잠겼어도 다시 보낸 화면은 "이미 저장된 콜입니다"를 받는다. 입력 형식 검사와 권한 검사는 그대로 먼저 돈다. 스펙 228줄을 "검사를 거쳐 거절"로 읽어야 한다면 순서만 바꾸면 된다.
  - 보내는 중과 "저장 여부 확인 중"에는 새 행 입력칸을 잠근다(전에도 보내는 동안 잠겼다). 다시 시도가 이미 저장됐을지 모르는 그 값을 보내야, 이미 있는 콜이 돌아왔을 때 그 사이 고친 값이 말없이 사라지지 않는다. 잠긴 동안 고른 가능 코스는 잠금이 풀린 뒤 채운다. 기존 행의 "응답 기다리는 동안 수정 모으기"(티켓 15)는 updatedAt이 있는 기존 행의 규칙이라 새 행에는 쓰지 않았다.
  - 응답이 15초 안에 오지 않아도 "저장 여부 확인 중"이 된다. 그 뒤에 온 응답은 받아들인다. 다시 보낸 저장을 기다리는 동안 온 앞 시도의 끊김·실패 소식은 버린다.
  - 다시 시도 버튼은 기존 문구 "재시도"(`calls.save.retry`)를 그대로 쓴다. "저장 여부 확인 중" 칩 문구는 공통 `SaveStatus`에 두 언어로 이미 있었고, 안내 문장과 "이미 저장된 콜입니다."를 두 언어로 더했다.
  - 요청 id는 `crypto.getRandomValues`로 만든 32자리 16진수다. `randomUUID`는 https가 아닌 주소(같은 망의 태블릿 등)에서 없다.
- 검증(운영 빌드, 전용 DB `vietnam_aesthetic_t16`·포트 3116): 단위 624개 통과, tsc 통과, 검증 스크립트는 기존 실패인 4-6만 실패. 새 E2E 2건(응답 유실 뒤 재시도: 서버가 만든 뒤 끊김 → 이미 만든 콜, 서버에 닿기 전 끊김 → 새 콜 / 실제 Postgres 동시 생성 4건)은 3회 반복 통과. 전체 병렬 실행(277개)의 실패 15개와 원장 관련 스펙을 합쳐 리뷰 반영 뒤 새 DB에서 직렬로 다시 돌리니 106개 통과, 2개 실패였다. 5-5:210은 기존 직렬 실패 목록에 있고 콜을 건드리지 않는다. ticket-04:209(휴대폰 폭 /live 카드 높이)는 앞의 현장 스펙(3-2·3-5)이 오늘 날짜 객실에 넣은 콜 때문이며 새 DB 단독으로는 통과한다. 원장 관련 스펙(2-1·2-2·2-3·2-4·2-6·5-4·i18n-vi·03·13·14·15·client-revision)은 모두 통과했다.
  - 서버를 띄운 직후 첫 실행에서 재시도 성공 뒤 원장 표 자동 갱신이 15초 넘게 늦은 적이 두 번 있었다(그 뒤 실행들은 0.3초 안). 메모리에 적힌 운영 빌드의 "서버 액션 결과가 화면에 반영되지 않는" 기존 문제(client-revision:310 등)와 같은 증상으로 보고, E2E는 다시 불러온 원장에서 그 콜이 한 줄인지 확인한다.
