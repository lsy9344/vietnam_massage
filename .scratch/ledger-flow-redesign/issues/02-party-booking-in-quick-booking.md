# 02: 빠른 예약 일행(여러 명) 예약

**What to build:** 콜에 일행 칸(`partyId`, `partyPosition`)을 추가하는 마이그레이션과 ADR 0007을 쓴다. 빠른 예약에서 인원 수를 받아 손님마다 코스·매니저·객실을 고르고, 일행 콜 N건을 한 트랜잭션으로 만든다. (스펙 D10–D13)

**Blocked by:** 01

**Status:** ready-for-agent

- [x] 마이그레이션은 칸 추가와 `partyId` 색인만 한다. 기존 콜은 둘 다 비어 있다. ADR 0007이 왜 별도 일행 표가 아니라 콜의 두 칸인지 남긴다.
- [x] 고객 단계에 인원 수(기본 1)가 있다. 1이면 지금 흐름과 결과가 같다(기존 E2E 통과).
- [x] 인원이 2 이상이면 매니저 단계에서 손님 1…N을 차례로 고른다. 손님마다 코스를 고르며 기본값은 손님 1의 코스다. 같은 매니저를 두 손님에게 고르면 막는다. D코스 손님의 두 번째 매니저 규칙은 손님마다 그대로다.
- [x] 객실 단계에서 손님마다 객실을 고르거나 비운다. 같은 객실 중복은 기존 겹침 경고 규칙을 따른다.
- [x] 확인 단계는 손님별 요약을 보인다.
- [x] 저장은 콜 서비스 작업 하나이고 N건을 한 트랜잭션으로 만든다. 한 건이라도 검증에 걸리면 아무것도 만들지 않고, 오류는 해당 손님·필드 옆과 요약에 나온다. 권한·운영월 잠금·활성 여부 검사는 한 건 저장과 같다.
- [x] 요청 id는 일행 저장 하나에 하나다. 같은 요청 id 재전송은 이미 만든 일행을 돌려준다(서비스 테스트).
- [x] 고객 연결은 1번 콜에만, 고객/메모는 모든 콜에 같다. 각 콜에 `partyId`와 1…N `partyPosition`이 들어간다. 콜마다 생성 감사 기록이 남고 일행 id가 담긴다.
- [x] PC·태블릿 폭 E2E: 3인 일행 저장 → 원장에 3건, 같은 시간·메모, 서로 다른 매니저. 새 문구는 ko·vi.

## Comments

- 2026-10-16 구현(브랜치 feat/ledger-flow-redesign).
  - 서비스 `createQuickBookingParty`, 액션 `createQuickBookingPartyAction`을 더했다. 인원 1명이면 패널은 지금까지의 한 건 저장(`createQuickBookingServiceCallAction`)을 그대로 쓴다.
  - 가정: 비고·방문별 요청도 고객/메모처럼 일행 모두에 같은 값으로 넣는다. 손님 Therapist는 한 건 예약처럼 비워도 저장된다(미배정 콜). 인원 상한은 10명이다(화면 선택 목록과 입력 검사).
  - 요청 id는 1번(대표) 콜에만 적고, 다시 보내면 그 콜의 `partyId`로 일행 전체를 돌려준다. 저장 전에 일행 공통 값(운영월 잠금, 시각, 상태 코드)을 먼저 보고, 손님마다 코스·객실·Therapist를 다 본 뒤에 쓰기 시작한다. 그래서 손님 검사에 걸리면 새 고객도 만들지 않는다. 1번 콜이 쓰인 뒤의 실패는 DB 트랜잭션 롤백에 맡기며, 메모리 가짜 DB에는 롤백이 없어 단위 테스트로는 확인하지 않았다. 같은 요청 id의 동시 저장도 같은 이유로 테스트하지 않았다(코드 경로는 한 건 저장과 같다).
  - 손님별 오류 키는 `guests.<손님 번호>.<칸>`이다(서비스 오류와 zod 거절 모두). 패널은 그 손님 줄에 "!"를, 요약에 "손님 N · …"를 보이고 누르면 그 손님으로 간다.
  - 화면: 고객 단계에 "인원", Therapist·코스 단계에 손님 줄(고르면 아직 안 고른 다음 손님으로 넘어감, 다른 손님이 고른 Therapist는 목록에서 빠짐), 객실 단계에 손님별 객실, 확인 단계에 인원과 손님별 요약. 코스를 고르지 않은 손님은 손님 1의 코스로 저장되고, 두 번째 Therapist 필요 여부도 그 코스로 본다.
  - 행 DTO에 `partyId`·`partyPosition`은 아직 넣지 않았다(원장 표시는 티켓 03·04). 감사 스냅샷에는 일행 콜일 때만 두 칸이 들어간다.
  - 검증: 단위 894개 통과, 운영 빌드 E2E(새 DB) 일행 스펙 1280·1024px와 빠른 예약 20·21·24 모두 14개 통과. 일행 E2E는 저장 뒤 원장 자동 새로고침이 운영 빌드에서 늦을 때가 있어 다시 불러온 뒤 행을 확인한다. `pnpm lint`의 story-4-6 검증기는 기준 커밋에서도 실패한다.
  - 마이그레이션 `20261017120000_add_service_call_party`는 새 DB에만 적용했다. 운영 DB 적용은 하지 않았다(D25).
